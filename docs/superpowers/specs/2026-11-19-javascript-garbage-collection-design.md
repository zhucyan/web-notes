# JavaScript 垃圾回收、可达性分析与内存泄漏定位文章设计

## 目标

在 JavaScript 系列中发布第八篇文章。文章从对象为何能被回收这一基础问题出发，解释可达性分析和 V8 的回收策略，并把原理连接到 Chrome DevTools 的内存泄漏定位工作流。

## 读者与写作原则

- 面向已具备 JavaScript 基础、希望理解浏览器内存问题并能独立排查的前端开发者。
- 使用“概念 → 运行时机制 → 泄漏模式 → 工具定位 → 排查闭环”的渐进主线：先建立正确心智模型，再给出可复现、可验证的实战方法。
- 区分 ECMAScript 层面的可达性概念和 V8 的具体实现：可达性是理解对象是否可回收的核心；分代、Scavenge、标记清除与压缩用于理解常见性能特征，不能作为业务代码的依赖。
- 所有代码示例独立、简短，泄漏示例必须同时给出对应的修复方式；不用人为频繁调用 GC 作为常规解决方案。

## 文章结构

1. **为什么需要垃圾回收**：解释内存、调用栈和堆的职责，说明内存泄漏是“不再需要的数据仍被持有”，通常表现为内存基线随操作次数上升，而非立即报错。
2. **可达性分析**：从 GC Roots、强引用和引用链开始，说明对象从根可达时不能回收、不可达时可回收；以全局对象、调用栈、闭包、DOM 与事件监听的引用路径建立直觉。
3. **V8 如何回收**：概览新生代与老生代，以及 Scavenge、标记、清除和整理的职责，解释停顿、晋升和“对象存活时间”的关系，并提示实现会随引擎版本变化。
4. **高频内存泄漏模式**：逐一说明意外全局变量、未移除的事件监听器、未清理的定时器/订阅、脱离文档的 DOM 节点，以及闭包或无上限缓存长期持有对象。每一项包含错误代码、引用链解释和修复代码。
5. **Chrome DevTools 定位方法**：介绍性能面板观察和 Memory 面板的 Heap Snapshot、Allocation instrumentation on timeline、Allocation sampling；讲清强制 GC、重复操作、前后快照对比、对象筛选与 Retainers 引用链的使用顺序。
6. **完整排查案例**：构造一个组件多次挂载与卸载后未移除全局事件监听器的案例。通过三次操作后的快照比较、定位 Detached DOM 或组件对象、沿 Retainers 找到监听器闭包，最终用显式清理修复，并验证内存基线稳定。
7. **排查清单与预防**：给出问题复现、建立基线、重复操作、采样、沿引用链定位、修复与回归验证的闭环；补充生命周期清理、缓存上限、取消订阅和监控指标等工程实践。
